# Downstream integration profiles

Generated by `cargo run -q -p axiolid-contracts --example downstream_profiles`. Do not edit by hand.

The v0.4 protocol supports three consumption profiles. These rows define boundary compatibility; they do **not** claim that every operation is available. A concrete build must return an `IntegrationDescriptor`, and an operation is advertised only after a provider implementing its operation trait is present and exercised. See [ADR 0039](../adr/0039-downstream-integration-contract.md).

## Boundary invariants

All profiles use right-handed Cartesian `f64` coordinates. Geometry is unitless: coordinates and every explicit tolerance use one caller-selected unit. Approximate or discretizing work requires a caller-visible tolerance. Exact requests either return exact analytic/topological results or typed refusal; they never silently return meshes. Rust values own their allocations. Native outputs are opaque handles released by their matching Axiolid destructor.

## Typed handshake

Consumers submit a `CapabilityRequirement` containing a versioned capability ID, required output representation, and required fidelity. `IntegrationDescriptor::require` returns the matching descriptor or a typed `RequirementRefusal` (`ApiVersion`, `CapabilityUnavailable`, `RepresentationUnavailable`, or `ExactnessUnavailable`). This check performs no fallback. Provider selection remains explicit and operation traits remain the capability truth.
